# [Docs] Проверить чистый запуск и подготовить честный сценарий демо Tandau

**Исполнитель:** @yassmn126  
**Приоритет:** средний, перед передачей версии на показ  
**Оценка:** 25–35 минут  
**Зависимости:** конкретный commit SHA от главного разработчика; реализованные сценарии показывать только после фактической проверки.

## Зачем

README должен позволять запустить проект без помощи команды. Нужен короткий сценарий демонстрации, который подтверждает только работающие функции и показывает ограничения данных. Основной README уже существует; задача — независимая проверка и точечные замечания, не переписывание архитектуры.

## Файлы

- Создать: `docs/DEMO_CHECKLIST.md`.
- Читать: `README.md`, `requirements.txt`, `.env.example`, `run.py`, `docs/01_REFERENCE.md` §4.
- На существующий раздел README «Языки интерфейса» есть отдельный владелец в issue i18n. Остальные замечания передать главному разработчику через `DEMO_CHECKLIST.md`, чтобы избежать одновременных правок README.
- Не менять `matcher/`, маршруты, авторизацию, БД и зависимости ради прохождения демонстрации.

## Проверка запуска

1. Записать SHA, ОС, версию Python и точные использованные команды. Использовать отдельную чистую папку/окружение, не трогать рабочую копию главного разработчика.
2. Выполнить шаги README как новый эксперт: установка зависимостей, запуск `python run.py`, открытие `http://127.0.0.1:8000`. Не создавать вручную файлы, которые README не требует.
3. Проверить отсутствие обязательной регистрации, `.env`, личных API-ключей и внешней БД для текущей версии.
4. Проверить `/healthz` → статус ok, 66 профилей; `/api/meta` → 17 категорий, 3 города и окно 2026-09-23–2026-12-31; `/openapi.json` открывается.
5. Проверить `/docs` при наличии сети. Записать известную оговорку: стандартный Swagger может получать ресурсы с CDN, тогда как сам интерфейс и JSON API работают локально после установки зависимостей.
6. Если другой ОС нет, пометить её команды как не проверенные; не утверждать проверку Windows по факту запуска на macOS.
7. Запустить существующий набор `python -m pytest -q`; записать итог и SHA. Если тесты падают, передать точное сообщение главному разработчику, не менять ожидания тестов ради зелёного результата.

## Демо текущей версии: 90–120 секунд

1. Одним предложением объяснить Tandau: до трёх event-подрядчиков с объяснениями по параметрам мероприятия.
2. На лендинге показать переключение RU → KK → EN и живую статистику: 66 профилей, 17 категорий, 3 города, календарь 100 дней.
3. Показать пример карточки: цена «от», объяснение по фактам и бейдж ориентировочной цены. Указать, что пример сейчас иллюстративный.
4. Показать различие «категории нет в городе» и «кандидаты есть, но условия не проходят» как объясняемые исходы; не выдавать статические примеры лендинга за работающий подбор.
5. Открыть `/healthz` или `/api/meta`, показать локальную загрузку каталога.
6. Коротко назвать фактический статус: auth/подбор/кабинет — заглушки, если это всё ещё так на проверенном коммите.

## Когда главный разработчик передаст готовый подбор

Сохранить в чек-листе таблицу: сценарий → введённые поля → ожидаемый статус из справочника → фактический результат → SHA. Порядок выдачи не выдумывать: справочник задаёт допустимые профили, а финальный порядок проверяется работающим движком.

| Сценарий | Запрос | Что подтвердить |
| --- | --- | --- |
| S1 | Алматы, 10.10.2026, корпоратив, Ведущий, 1 500 000 ₸, 6 ч | `found`, 5 проходят, до 3 карточек и «ещё 2» |
| S2 | Алматы, свадьба, Ведущий, 1 000 000 ₸, казахский, 8 ч; 10.10 → 17.10 | `partial` → `found`, объяснение изменения занятостью |
| S3 | Алматы, 10.10.2026, той, Ведущий церемонии, 300 000 ₸, казахский | `partial`, один результат, причина нехватки |
| S4 | Астана, 14.11.2026, свадьба, Декоратор, 2 500 000 ₸ | `no_category_in_city` |
| S5 | Алматы, 26.12.2026, той, Ведущий, 700 000 ₸ | `none_match`, причины и честные подсказки |

Для 2-минутного живого показа выбрать 3 сценария, но перед сдачей проверить все доступные. S6 (зал) и S7 (дата вне окна) остаются в справочнике для дополнительной проверки, если движок уже готов.

## Критерии приёмки

- [ ] `DEMO_CHECKLIST.md` содержит SHA, окружение, команды и результат чистого запуска.
- [ ] Показ возможен без личных аккаунтов участников; если позже понадобится демо-аккаунт, он проверен после реализации auth, а не скопирован из плана как существующий.
- [ ] Работающие функции, иллюстрации, заглушки и планы явно различены.
- [ ] Указаны анонимизация, 13 синтетических профилей, цена «от» и ограниченный календарь.
- [ ] Есть короткий сценарий на 90–120 секунд и резервный порядок действий при недоступном интернете.
- [ ] Не требуется открывать личные переписки, ключи или аккаунты для показа.
- [ ] Отмечены конкретные расхождения с README; главный разработчик получил их до итоговой сдачи.
- [ ] Для нереализованных S1–S5 стоит «не реализовано/не проверено», а не фиктивный pass.

**Границы:** не выполнять финальную отправку на платформе, не менять репозиторий сдачи и не создавать работающую авторизацию/подбор в рамках документационной задачи. Пример коммита: `docs: add verified demo and clean-start checklist`.
