### 2.1 Перенос оформления, появившийся во время подготовки плана

Коммит `758a221` уже переносит композицию дизайнбука на `/`, обновляет три словаря, добавляет `components.css`, общие макросы `icons.html` и карточку `partials/card.html`. Краткий бриф теперь содержит пять именованных полей, включая формат, и отправляет GET на `/app`.

`/app` теперь показывает редактируемый образец с переданными query-значениями и отключённой кнопкой подбора. Авторизация остаётся оформленными заглушками. Это реальный прогресс интеграции, который нужно использовать, а не создавать заново.

До приёмки по этому плану остаются следующие различия.

- Стартовые условия ещё предзаполнены демонстрационными значениями. План требует пустое состояние и явное заполнение примером.
- Query читается в шаблоне; отдельная серверная проверка пяти условий и состояние готовности не реализованы.
- Нет versioned sessionStorage, синхронизации URL после правок, подтверждения замены и полной очистки черновика.
- Карточка события в hero пока фиксированная, а не связанная с личным брифом.
- Категории показывают общие числа и ведут напрямую на `/app`; требуется обзор по локации с сохранением текущих условий.
- В публичном примере остаются временные закладки. План оставляет такие демонстрационные взаимодействия в дизайнбуке и убирает из публичного пути фазы 1.
- Гостевой экран пока является редактируемым макетом. Целевое поведение этой фазы — проверенная сводка с точными переходами редактирования.

Пакеты P1-B и P1-C начинать со сверки этого коммита с критериями, сохраняя подходящие компоненты и переводы. Кодовая работа в этой редакции документа не выполняется. Статус фазы остаётся «не принята» до полной проверки.

## 3. Граница результата

### 3.1 Обязательный объём

- Основной лендинг на `/` соответствует утверждённому визуальному направлению.
- Все продуктовые тексты, подписи ошибок и доступные названия элементов работают на RU/KK/EN.
- Бриф содержит город, дату, формат, категорию и бюджет на одного подрядчика.
- Условия можно редактировать, проверить, перенести на `/app` и вернуть в форму.

- Категории показывают численность по выбранной локации, без обещания доступности на дату.
- Пример рекомендаций использует настоящие записи CSV и фиксированный сценарий.
- Публичные кнопки имеют работающие назначения. Макеты остаются отдельными страницами для команды.
- Основной путь работает на телефоне, с клавиатурой и без обязательного JavaScript.
- README точно описывает границы реализованного этапа.

## 4. Продуктовая идея и отбор решений

Tandau помогает организатору сформулировать запрос и сравнить ограниченное число кандидатов. Визуальный язык строится вокруг документов события, оборудования и условий выбора.

Основной образ — **карточка события**. Крупная дата, выбранная услуга и бюджет образуют предметную композицию. Та же информация переходит из первого экрана в форму и гостевой экран. Пользователь видит непрерывность своего запроса.

### 4.1 Идеи, которые берём

| Идея | Как выглядит | Практическая ценность | Объём |
| --- | --- | --- | --- |
| Карточка события | Типографическая панель с датой, городом, услугой и бюджетом | Даёт Tandau собственный визуальный образ и отражает реальные данные формы | Обязательно |
| Запрос без повторного ввода | Черновик между лендингом, языками и `/app` | Убирает потерю уже введённых условий | Обязательно |
| Каталог по локации | Строки категорий с численностью для Алматы, Астаны и зарубежья | Показывает покрытие каталога до отправки запроса | Обязательно |
| Объяснение рядом с ценой | В примере цена, запас бюджета и факт профиля стоят рядом | Помогает сравнивать конкретные ограничения | Обязательно |
| Разбор происхождения данных | Раскрытие «На чём основан пример» с ID и флагами | Делает качество данных видимым | Обязательно |
| Заполнить примером | Отдельное действие загружает фиксированный сценарий | Позволяет быстро изучить форму без скрытых значений по умолчанию | Обязательно |
| Редактирование из сводки | Каждое условие ведёт в своё поле | Сокращает путь исправления | Обязательно |
| Предметная 3D-серия | Микрофон, камера, календарь и другие объекты из брифов | Поддерживает тему мероприятий | После получения файлов |

| --- | --- | --- |

### 4.3 Идеи, которые отклоняем

| Идея | Причина |
| --- | --- |
| Автоматический подбор всей команды мероприятия | Контракт работает с одной категорией за запрос; общий бюджет команды отсутствует |
| Ползунок «качество кандидата» и проценты совпадения | Нет достоверной шкалы качества или вероятности успеха |
| Генерируемые лица для анонимизированных профилей | Создают ложное впечатление реальной личности |
| Общая абстрактная 3D-жидкость | Не объясняет услуги, событие или выбор |
| Чат вместо пяти явных полей | Усложняет проверку условий и воспроизводимость без пользы для первого релиза |
| Регистрация перед знакомством с подбором | Нарушает гостевой сценарий |
| Отдельный конструктор мероприятий | Увеличивает объём без улучшения ключевого запроса |

## 5. Основной путь посетителя

### 5.1 Первый визит

1. Посетитель видит название Tandau, назначение сервиса и действие «Задать условия».
2. При желании открывает фиксированный пример через «Посмотреть пример».
3. Выбирает локацию, дату, формат, одну категорию и бюджет.
4. Проверяет карточку события. Пустые значения обозначены прямо.
5. Нажимает «Продолжить».
6. При клиентской ошибке остаётся в форме. Без JavaScript сервер показывает ошибки на `/app` и ссылки возврата в нужные поля с сохранёнными условиями.
7. При корректных условиях открывает `/app` со своей сводкой.
8. До подключения движка видит «Условия готовы. Сейчас можно посмотреть пример подбора» и два действия «Изменить условия» и «Посмотреть пример».

Последний шаг отражает текущую возможность продукта. На экране нет номеров фаз, технических флагов, названий API или обещания уже выполненного поиска.

### 5.2 Возврат в текущей вкладке

Форма восстанавливает последний черновик. Над ней появляется спокойная строка «Условия восстановлены в этой вкладке» и действие «Очистить». Персональных имён, контактов и паролей в черновике нет.

Вкладка или браузер могут восстановить sessionStorage при восстановлении сессии. Поэтому интерфейс не обещает гарантированное удаление при закрытии вкладки. Действие «Очистить» удаляет черновик явно.

### 5.3 Посетитель сначала изучает каталог

Посетитель выбирает локацию в блоке категорий, видит число профилей, нажимает нужную категорию и попадает в соответствующее поле брифа. Остальные условия не сбрасываются. При нулевой численности категория остаётся доступной, рядом показывается «В каталоге пока нет профилей в этой локации».

### 5.4 Посетитель открывает прямую ссылку

Пять базовых условий в URL `/app` воспроизводят сводку без аккаунта. Некорректная ссылка не превращается в успешный запрос. Страница показывает, что исправить, и возвращает к соответствующему полю.

## 6. Лендинг по секциям

### 6.1 Порядок блоков

```text
Шапка
Главный тезис + карточка события
Бриф из пяти условий
Три шага подбора
Пример рабочего экрана и трёх профилей
Каталог по локациям
Объяснение ограничений данных
Вопросы
Финальное действие
Подвал
```

У каждой секции одна задача. Не повторять одну и ту же статистику в трёх местах и не добавлять декоративные английские подписи над русскими заголовками.

### 6.2 Шапка

На десктопе слева знак трёх полос и слово `tandau`. В центре «Как работает», «Категории», «Пример». Справа выбор RU/ҚАЗ/EN и основное действие «Задать условия».

Пока реальный вход недоступен, не занимать шапку кнопками регистрации и входа. Маршруты `/login` и `/register` остаются доступными по прямому адресу с корректной заглушкой. После фаз 2–3 шапка получает эти действия через общий шаблон.

Шапка высотой от 72 px, белая, с нижней границей 1 px. Она остаётся сверху при прокрутке. Якорные секции используют `scroll-margin-top`, чтобы заголовок не скрывался. На узком экране видны знак, название и кнопка меню; основное действие находится внутри раскрытого меню и в hero.

Мобильное меню раскрывается в потоке под шапкой. Это обычная навигация, не диалог. Escape закрывает её и возвращает фокус кнопке. Переход по ссылке закрывает меню. При переходе на десктоп состояние сбрасывается.

### 6.3 Первый экран

**Заголовок**

> Соберите команду вашего события.

**Описание**

> Выберите услугу, город и дату. Сравните до трёх подрядчиков по условиям запроса.

**Уточнение**

> Одна категория в каждом запросе.

Заголовок выражает общую задачу организатора. Уточнение устраняет обещание автоматической сборки всей команды. На промежуточной версии рядом с примером есть подпись «Сейчас доступен пример подбора». После фазы 4 она заменяется на «Подбор без регистрации» только вместе с рабочим гостевым поиском.

Два действия — чёрное «Задать условия» и текстовое «Посмотреть пример». Первое ведёт к брифу, второе к секции примера. Оба переносят клавиатурный фокус к заголовку целевой секции, а не оставляют его в начале страницы.

Под действиями одна строка метрик из каталога. 66 профилей, 17 категорий, 3 локации. «Зарубежье» не называется городом. Не писать «66 свободных подрядчиков».

### 6.4 Карточка события в hero

Композиция из утверждённого макета сохраняется, но связывается с пользовательскими полями.

| Строка | Пустое состояние | Заполненное состояние |
| --- | --- | --- |
| Локация | Выберите локацию | Алматы |
| Дата | Дата события | 17 октября 2026 |
| Формат | Формат мероприятия | Свадьба |
| Категория | Кого ищете | Ведущий |
| Бюджет | Бюджет на подрядчика | До 1 000 000 ₸ |

Дата использует крупную цифру дня и отдельные месяц и год. До выбора даты показывается короткий текст, без выдуманного дня. Внизу «Заполнено 3 из 5 условий» отражает число валидных полей. Это не процент готовности мероприятия.

В стартовом состоянии карточка не содержит монограммы трёх кандидатов. Монограммы принадлежат только подписанному примеру ниже. Не показывать потенциальные результаты рядом с изменяемыми условиями до появления движка.

Карточка не является изображением. Все значения доступны как текст. Изменения объявляются одной сдержанной `aria-live="polite"` сводкой после завершения ввода, а не на каждый введённый символ бюджета.

### 6.5 Бриф

Заголовок «Условия события». Под ним «Одна услуга и бюджет на одного подрядчика».

На десктопе бриф делится на две строки. Первая содержит локацию, дату и формат. Вторая содержит категорию и бюджет. Формат не прячется в необязательные настройки. На мобильном поля идут в том же логическом порядке одной колонкой.

Под полями расположены основное действие «Продолжить», текстовое «Заполнить примером» и «Очистить». Подробное поведение каждого поля описано в разделе 9.

Текст о хранении появляется рядом с восстановленным черновиком. До первой записи не показывать сообщение «Сохранено».

### 6.6 Как работает подбор

Три колонки с общей верхней линией, порядковым номером и коротким объяснением. Номера здесь обозначают последовательность действий.

| Шаг | Заголовок | Текст |
| --- | --- | --- |
| 1 | Задайте условия | Город, дата, формат, категория и бюджет на подрядчика. |
| 2 | Сравните варианты | Посмотрите стартовую цену и факты, на которых основано объяснение. |
| 3 | Уточните выбор | Проверьте ограничения данных и условия, которые требуют подтверждения. |

До фазы 4 заголовок секции «Как устроен подбор» и подпись «Пример результата ниже». Формулировки описывают устройство сервиса и не утверждают, что запрос уже обработан. Сохранение в аккаунт не входит в эту последовательность до фазы 6.

### 6.7 Пример рабочего экрана

Это главный блок доказательства ценности. Он имеет собственную рамку, левую навигацию, верхнюю строку условий и три карточки.

Над рамкой крупно «Пример подбора». Под заголовком полный фиксированный запрос. Рядом с карточками подпись «Подготовленный пример из каталога. Условия вашей формы его не меняют».

Внутри рамки слева показана **сводка примера**, а не пользовательского черновика. Единственный активный пункт навигации «Пример подбора». Пустые разделы истории и избранного не показываются. Верхняя строка содержит название сценария и доступный переход «Заполнить форму этим примером».

Карточки и раскрытия описаны в разделе 12. Избранное из макета не переносить в публичную страницу фазы 1. Так у пользователя не появляется два разных обещания сохранения.

### 6.8 Каталог по локациям

Заголовок «Какие услуги есть в каталоге». Переключатель «Все локации / Алматы / Астана / Зарубежье». Значение «Все локации» существует только в обзоре каталога, в запрос оно не передаётся.

Категории представлены строками или прямоугольными кнопками с названием, числом профилей и стрелкой. На десктопе сетка из трёх колонок, на телефоне одна. Длинные названия переносятся без обрезки.

По умолчанию обзор следует за выбранной в брифе локацией. При пустом брифе показывает все локации. Изменение переключателя на конкретную локацию обновляет поле города и сводку. Выбор «Все локации» меняет только обзор и оставляет заполненный город брифа.

Нажатие категории сохраняет её каноническое значение и переводит фокус в поле категории. Если город ещё пуст, после выбора категории показывается обычная подсказка выбрать город; сам город не угадывается.

Сортировка остаётся стабильной по исходному порядку `catalog.category_rows()`. При смене города числа меняются, строки не прыгают. Ноль показывается явно. Пояснение под блоком сообщает, что один профиль может относиться к нескольким категориям и числа не обозначают доступность на дату.

### 6.9 Ограничения данных

Компактный блок с тремя строками.

- Каталог анонимизирован и предоставлен для демонстрации.
- Часть профилей синтетическая. Проставленные при подготовке цена и город отмечаются отдельно.
- Цена «от» и календарь каталога требуют подтверждения для реального заказа.

Число синтетических профилей берётся из `stats.synthetic`. Не превращать эти ограничения в длинный юридический текст и не скрывать их только в footer.

### 6.10 Вопросы

Нативные `<details>` с одним вопросом в строке, плюсом при закрытом и минусом при открытом состоянии. Несколько ответов могут быть открыты одновременно.

| Вопрос | Содержание ответа фазы 1 |
| --- | --- |
| Что уже можно сделать? | Задать условия, сохранить их в этой вкладке и изучить подготовленный пример. Подбор по новым условиям пока недоступен. |
| Нужна ли регистрация? | Для формы и примера не нужна. Поиск также будет доступен гостям после его подключения. |
| Что означает бюджет? | Максимальная стартовая цена одного подрядчика выбранной категории. Это не общая смета мероприятия. |
| Почему показано до трёх профилей? | Сервис рассчитан на короткую подборку. В примере показаны три заранее выбранные записи; это не результат текущей формы. |
| Откуда сведения? | Анонимизированный CSV организаторов. Указать актуальное число профилей и происхождение флагов. |
| Можно ли забронировать? | Бронирования и оплаты в Tandau нет. |
| Сохранятся ли мои условия? | В этой вкладке при доступном хранилище браузера. Есть отдельное действие очистки; аккаунтное хранение ещё не подключено. |

Тексты меняются вместе с фактической функцией в последующих фазах. Не оставлять ответ «подбор уже работает» в промежуточной версии.

### 6.11 Финальный блок и подвал

Чёрный фон, белый заголовок «Начните с условий события». Белая кнопка «Задать условия» ведёт в существующий бриф. Восстановленный запрос не сбрасывается.

Подвал содержит Tandau, краткое описание проекта и ссылки «Категории», «Пример», «Вопросы». Ссылка API находится в отдельной строке «Для проверки проекта». Не добавлять фиктивные социальные сети, контакты, партнёров, отзывы и юридические страницы.

## 7. Гостевой экран `/app`

### 7.1 Назначение в фазе 1

Экран подтверждает, что условия дошли до приложения. Он не вызывает подбор и не создаёт запись в БД.

Десктопная композиция использует боковую область 224 px, верхнюю строку и основную поверхность. В боковой области логотип, активный пункт «Условия», ссылка «Пример» и обозначение «Гость». Основная поверхность содержит заголовок «Ваш запрос», пять значений и состояние готовности.

У каждого значения доступно действие «Изменить», которое ведёт на `/#brief-<field>` с переносом текущих пяти условий. При JavaScript данные дополнительно сохраняются в черновик. Без JavaScript значения сохраняются в query-параметрах ссылки.

### 7.2 Состояния

| Условие | Что видно | Следующее действие |
| --- | --- | --- |
| Прямой `/app`, нет черновика | «Задайте условия события» | «Заполнить форму» → `/#brief` |
| Есть неполный черновик | Введённые значения, отсутствующие условия названы | «Дополнить условия» → первое пустое поле |
| Все пять значений валидны | Полная сводка, «Условия готовы» | «Изменить условия», «Посмотреть пример» |
| Значение в URL невалидно | Сводка с конкретной ошибкой, без успеха | Исправить это поле |
| Движок ещё отсутствует | «Сейчас можно посмотреть пример подбора» | `/#example` |
| Хранилище недоступно | Текущая сводка работает через URL | Текст о недоступном автосохранении только если запись действительно не удалась |

Никаких счётчиков найденных кандидатов, спиннера поиска, готовых карточек под личными условиями и кнопки «Подобрать» с фиктивным ответом.

### 7.3 После фазы 4

Тот же `/app` получает поиск и реальные результаты. Блок ограничения исчезает, сводка становится редактируемыми условиями. Фаза 4 использует те же query-имена и проверяет их сервером заново. Это точка подключения будущего движка, а не новая система маршрутов.

Фаза 1 не добавляет пользовательский параметр `matching_available=1`. Факт наличия обработчика определяется приложением. Пользователь не может включить отсутствующую функцию через URL или localStorage.

Очистка после подтверждения «Очистить условия?» удаляет значения, ошибки и ключ хранения, сбрасывает счётчик до 0 из 5 и переводит фокус на заголовок формы. Очистка не удаляет cookie языка и не затрагивает будущую сессию входа.

## 9. Спецификация каждого поля

### 9.1 Общие правила

Все пять полей обязательны. Над формой есть короткое пояснение «Заполните все пять условий». У каждого контрола постоянная видимая подпись. Placeholder не заменяет label. Ошибка связана через `aria-describedby`, невалидный контрол получает `aria-invalid="true"`.

Ошибки показываются после попытки продолжить или после ухода из уже изменённого поля. При первом открытии пустая форма не окрашена в красный. После неудачной отправки фокус переходит к сводке ошибок; каждая строка сводки ведёт к полю.

Исходные значения пустые. Алматы, свадьба, 17 октября и миллион тенге заполняются только явным выбором примера. Наличие популярных условий не позволяет выбрать их за пользователя.

### 9.2 Локация

| Параметр | Решение |
| --- | --- |
| UI | Три прямоугольные radio-плитки с общей подписью «Город или локация» |
| Значения | `Алматы`, `Астана`, `Зарубежье` |
| HTML name | `city` |
| Выбор | Одна плитка; нативный radio и клавиши стрелок |
| Вид выбранного | Чёрная граница, синяя короткая отметка, заполненный radio |
| Ошибка | «Выберите город или локацию» |
| Недопустимое значение | «Этой локации нет в каталоге» |

Под плиткой можно вывести число профилей **в каталоге**, рассчитанное по текущим данным. Оно не зависит от даты или бюджета. Изменение локации не удаляет уже выбранную категорию.

### 9.3 Дата события

| Параметр | Решение |
| --- | --- |
| UI | Белое поле даты и отдельная чёрная типографическая метка дня |
| HTML | `input type="date"`, `name="date"` |
| Допустимо | 2026-09-23…2026-12-31 включительно |
| Пустое состояние | Нативный формат ввода, рядом «Выберите дату» |
| Невалидная дата | «Укажите существующую дату» |
| Вне окна | «Выберите дату с 23 сентября по 31 декабря 2026 года» |

Для первой реализации использовать нативный календарь. Внешняя композиция поля остаётся собственной. Кастомный календарь из дизайнбука переносить только отдельным улучшением после выполнения обязательной приёмки, с проверкой клавиатурной навигации. Он не является зависимостью готовности фазы.

Дата хранится как строка ISO без часового пояса. Не преобразовывать её через UTC timestamp так, чтобы день изменился в другой зоне. Границы берутся из `catalog.meta().window`, а не из текущей даты устройства или ближайшей занятой даты.

Поле не показывает доступность подрядчиков и не окрашивает день зелёным как «свободный».

### 9.4 Формат мероприятия

| Параметр | Решение |
| --- | --- |
| UI | Шесть radio-плиток с функциональной иконкой и коротким названием |
| HTML name | `event_type` |
| Канонические значения | `свадьба`, `той`, `корпоратив`, `конференция`, `юбилей`, `день рождения` |
| Структура | `fieldset` и `legend`, выбор одного значения |
| Ошибка | «Выберите формат мероприятия» |

Плитки распределяются в три колонки на широком экране и две на узком, если текст помещается. Иначе одна колонка. «Той» и «свадьба» остаются разными значениями из CSV. Перевод не объединяет их.

Иконка помогает сканировать форму. Она не заменяет текст и не требует 3D-ассета. Выбор формата не меняет город, дату и категорию.

### 9.5 Категория подрядчика

| Параметр | Решение |
| --- | --- |
| UI | Высокое поле с номером шага в подписи, нативным select и строкой покрытия каталога |
| HTML name | `category` |
| Данные | Все 17 значений из `catalog.category_rows()` |
| Пустое значение | «Выберите услугу» |
| Вспомогательный текст | «Профили в каталоге по этой локации — 10» либо «Выберите локацию, чтобы увидеть число профилей» |
| Нулевое покрытие | «В каталоге нет этой услуги в выбранной локации» |
| Ошибка | «Выберите категорию из каталога» |

Ноль является сведением о каталоге, а не ошибкой формы. Запрос остаётся валидным и позднее может получить `no_category_in_city`. Не отключать категории с нулём и не подменять их ближайшей услугой.

«Ведущий» и «Ведущий церемонии» сравниваются как целые значения. Поиск по подстроке здесь недопустим. Переведённая подпись option не меняет `value`.

### 9.6 Бюджет

| Параметр | Решение |
| --- | --- |
| UI | Крупное число, постоянный знак ₸, подпись «Бюджет на подрядчика» |
| Canonical | Положительное целое число тенге |
| HTML name | `budget` |
| Дополнительные действия | 500 000, 1 000 000, 2 000 000 ₸ |
| Пустое состояние | «Введите сумму» |
| Ошибка нуля/минуса | «Бюджет должен быть больше нуля» |
| Ошибка дроби/текста | «Введите целую сумму в тенге» |

Базовый контрол — `input type="text" inputmode="numeric"`. Допускаются обычные, неразрывные и узкие неразрывные пробелы между цифрами. Перед проверкой их удалить. Разрешены только десятичные цифры, без минуса, десятичной точки, запятой, экспоненты и символа валюты в значении.

`1 000 000` превращается в `1000000`. `1e6`, `1,5`, `1000.50` и `₸1000` отклоняются. Ведущие нули допустимы и нормализуются. Пустое значение отличается от нуля.

Для точной передачи между браузером и Python использовать максимум `9007199254740991` ₸. Это предел целого числа формата передачи, не рыночное ограничение. При превышении сообщить «Сумма слишком велика для обработки». Указать тот же технический предел будущему валидатору API.

Кнопки сумм имеют `type="button"`. Они заменяют значение и синхронизируют карточку события. Пользователь может ввести любую допустимую сумму вне предложенных вариантов.

Ползунок из дизайнбука не обязателен для лендинга. Если он переносится позже, его шкала не ограничивает ручной ввод и не округляет скрытно введённую сумму. Бюджет не преобразуется в рейтинг кандидата.

### 9.7 Зарезервированные дополнительные условия

В фазе 1 они не показаны в публичном брифе. Их контракт фиксируется для фазы 4.

| Поле | Контракт | Будущий компонент |
| --- | --- | --- |
| `duration_h` | `null` или целое 1–24 | Степпер и «Не ограничивать» |

### 10.4 Ошибки и HTTP

Страница `/app` возвращает HTML 200 для пустого, неполного и невалидного черновика. Частичная ссылка вида `/app?city=Алматы&category=Ведущий` является намеренным предзаполнением. Для отсутствующих полей показываются приглашения дополнить условия, без красных ошибок до попытки отправить форму. Присутствующее некорректное значение получает конкретную ошибку. Состояние видно в содержимом. Это форма для исправления условий, а не API `SearchResponse`. Будущие JSON-статусы `found`, `partial`, `none_match` здесь не используются.

Пять параметров запроса валидируются по allowlist и типам. Неизвестные дополнительные query-параметры не попадают в шаблон и хранилище. Повтор одного базового параметра считается ошибкой конкретного поля, чтобы разные уровни приложения не выбрали разные значения.

Невалидное исходное значение сохраняется для исправления в безопасно экранированном виде. Не применять Jinja `safe` к значениям пользователя. URL строить стандартным кодированием параметров, без конкатенации строк из ввода.

## 11. Черновик и синхронизация

### 11.1 Место хранения

Ключ `tandau.brief.v1` в `sessionStorage`. Запись локальна для вкладки и текущего origin. Она не является историей аккаунта и не передаётся в cookie сессии.

```json
{
  "version": 1,
  "values": {
    "city": "Алматы",
    "date": "2026-10-17",
    "event_type": "свадьба",
    "category": "Ведущий",
    "budget": "1000000"
  },
  "updated_at": "2026-09-23T10:00:00.000Z"
}
```

`values` хранит пять строк, чтобы черновик мог быть частично заполненным. `updated_at` нужен для отладки восстановления и не задаёт срок годности. Выбранный язык хранится существующим механизмом языка, не дублируется в этой записи.

Записывать после `change`, после blur текстового бюджета и перед внутренним переходом. Не писать на каждый вводимый символ. Ошибки и признак `complete` не хранить, они пересчитываются.

После каждого такого изменения одновременно обновлять текущий URL через `history.replaceState`. Записать все пять текущих строк, включая пустые, сохранить `lang` и уместный hash. Это правило действует для ручного ввода, выбора категории, суммы и заполнения примером. Новая запись истории браузера не создаётся. Если storage недоступен, URL всё равно обновляется. Так явный снимок URL остаётся актуальным, и refresh не заменяет изменённый бюджет старым значением. Полная очистка является исключением и удаляет все пять параметров.

Пример проверки. Открыть ссылку с миллионом, изменить бюджет на два миллиона, покинуть поле и обновить страницу. И поле, и сводка должны остаться на двух миллионах. При загрузке чужой частичной ссылки старое storage всё равно не дополняет её.

### 11.2 Приоритет источников

1. Явные параметры базового запроса в текущем URL.
2. Валидная по структуре запись `tandau.brief.v1` при отсутствии базовых параметров в URL.
3. Пустая форма.

Если в URL присутствует хотя бы один базовый параметр, это отдельный снимок запроса. Недостающие поля остаются пустыми. Не смешивать чужую прямую ссылку с прежними значениями вкладки.

`?lang=en` не считается снимком запроса. При смене языка черновик восстанавливается. Явное заполнение примером заменяет все пять значений после подтверждения, когда оно нужно.

Если `/app` открыт без базовых query-параметров, но в storage есть структурно корректный непустой черновик, JS один раз выполняет `location.replace` на `/app` с его пятью значениями. Сервер повторно проверяет их и рендерит сводку. Пустая или повреждённая запись не вызывает переход. Наличие базовых параметров прекращает восстановительный переход и предотвращает цикл. Клиент не объявляет запрос готовым в обход сервера.

### 11.3 Повреждённые данные

Неверный JSON, неизвестная версия или неправильная структура игнорируются без падения страницы. Неизвестные ключи отбрасываются. Строковые значения проходят те же проверки при продолжении, что и обычный ввод.

Для защиты от случайной огромной записи установить лимит чтения 16 KiB. Это лимит контейнера из пяти коротких значений. Нельзя молча обрезать сумму или название категории и считать их валидными.

Если запись или чтение storage вызывает исключение, форма продолжает работать. При попытке сохранить показать «Автосохранение в этой вкладке недоступно». GET-переход и ссылки редактирования сохраняют текущие базовые условия.

### 11.4 Язык, история браузера, очистка

Перед сменой языка JS сохраняет текущую форму. Ссылка смены языка включает текущие пять условий в безопасный локальный путь возврата либо использует существующий `/lang/{code}` с Referer, уже содержащим эти условия. Нельзя допускать потерю полей при браузерной политике Referer.

Для надёжного варианта добавить в существующий языковой маршрут необязательный `next` только как относительный локальный путь. Валидатор должен отвергать внешние адреса, `//`, обратные слэши, управляющие символы и их закодированные варианты. При ошибке возврат на `/`. Если `next` отсутствует, сохранить существующий безопасный Referer-fallback. Нужны регрессионные проверки обоих путей.

Без JS смена языка может сохранять только значения из текущего URL. Несохранённый ввод без отправки не обещает сохранения. Основная GET-форма остаётся работоспособной.

После явной очистки убрать базовые параметры из адреса через `history.replaceState`, сохранив `lang` и уместный hash. Иначе обновление снова заполнит форму удалёнными значениями. На событие `pageshow` после Back/Forward синхронизировать DOM, сводку и запись; не перезаписывать явный снимок URL устаревшим storage.

### 11.5 Совместимость с авторизацией

Планы фаз 2–3 очищают содержимое cookie-сессии при входе и выходе. Поэтому черновик не класть в `request.session`. В будущем после авторизации возвращаться на безопасный короткий `/app`, затем читать черновик из sessionStorage по правилу раздела 11.2. Существующий план фазы 6 предлагает переносить пожелания в URL повторного запроса. Перед его реализацией изменить этот переход на передачу через тело запроса или серверный ID сохранённой записи. Свободный текст не возвращать в query.

Черновик не превращается в историю пользователя автоматически. Постоянное сохранение требует реализации фазы 6. Пожелания, пароли и email не добавлять в `next` или URL возврата.

Данные о дате формулировать «На 17 октября нет отметки занятости в каталоге». Не писать «гарантированно свободен» или «доступен для бронирования».

Фаза 1 выносит навигацию, кнопки, label/hint/error, notice, карточку события и источники профиля в переиспользуемые шаблоны. Email и пароль остаются компонентами дизайнбука до фаз 2–3. Рабочие формы авторизации здесь не создаются.

## 14. Адаптивность и доступность

| Ширина | Hero | Бриф | Пример приложения |
| --- | --- | --- | --- |
| От 1200 px | Две колонки | Две строки | Sidebar + три карточки, если каждая не уже 240 px |
| 768–1199 px | Две колонки при достаточной ширине, иначе одна | Две колонки | Компактная сводка над карточками, карточки в одну или две колонки |
| 360–767 px | Одна колонка, текст перед карточкой | Одна колонка | Вертикальная сводка и карточки |
| 320 px | Та же структура без горизонтальной прокрутки | Один контрол в строке | Все сведения доступны переносом |

На мобильном рабочий sidebar становится компактным блоком сверху, а не фиксированным drawer. Верхняя строка не создаёт второй липкий бар поверх основной шапки.

Обязательные проверки.

- Весь путь доступен Tab, Shift+Tab, Enter, Space и стрелками нативных radio.
- Один H1 на страницу, секции с H2, имена профилей с H3.
- Skip-link переводит фокус в main.
- Фокус виден на белом, сером и чёрном фоне.
- Масштаб 200% не скрывает действия; длинный казахский текст переносится.
- Ошибки содержат причину и способ исправления.
- Контраст обычного текста от 4.5:1, крупных надписей и существенной графики от 3:1.
- У иконок без текста есть доступное имя; декоративные SVG имеют `aria-hidden`.
- Форма работает без hover; все подсказки доступны касанием и клавиатурой.
- Динамическая сводка не объявляется целиком при каждом нажатии клавиши.
- Нет обязательной анимации, автопрокрутки без действия пользователя или автоматического перелистывания примеров.

### 14.1 Поведение без JavaScript

Серверный HTML сразу содержит всю навигацию, контент, пять нативных полей и submit. Только успешно запущенный JS добавляет состояние улучшенного интерфейса и сворачивает мобильную навигацию. Кнопка раскрытия меню до этого скрыта.

| Элемент | Без JavaScript | После инициализации |
| --- | --- | --- |
| Основные якоря и ссылки | Обычные переходы | Дополнительно управляют фокусом |
| Форма | GET на `/app`, проверка сервером | Клиентские ошибки, синхронизация сводки и черновика |
| Категория в обзоре | Ссылка к полю категории | Дополнительно заполняет выбранное значение |
| Заполнить примером | Не показывается | Кнопка с подтверждением замены |
| Очистить | Не показывается; значения можно удалить в полях и отправить форму | Подтверждение, очистка storage и URL |
| Кнопки сумм | Не показываются | Заполняют бюджет |
| Мобильное меню | Ссылки видны в потоке | Раскрытие кнопкой и закрытие Escape |
| FAQ и источники | Нативные details работают | То же поведение |
| Живая карточка события | Отражает значения серверного снимка | Обновляется после изменения полей |

Не выводить видимую неработающую кнопку как fallback. Под формой в `noscript` коротко сообщить «Условия появятся на следующем экране после отправки формы». Автосохранение и мгновенное обновление сводки без JS не обещаются.

## 15. Тексты и три языка

### 15.1 Правила

Все новые видимые строки идут через `t()`. Данные каталога выводятся через `label(kind, value)`. `ru`, `kk`, `en` обозначают язык интерфейса. В API остаются исходные значения CSV.

Не копировать русские строки напрямую из `landing_sample.html` в новый продуктовый шаблон. Отдельно переводить ошибки, `aria-label`, диалоги, подписи чисел, alt, title и сообщения восстановления.

Главный разработчик фиксирует ключи и русские значения. yassmn126 редактирует казахский и английский в рамках того же набора. Ключи не переименовываются в одной языковой версии отдельно.

### 15.2 Реестр новых групп ключей

| Группа | Обязательные строки |
| --- | --- |
| `landing.hero.*` | Заголовок, описание, одна категория, две CTA, текущая возможность |

| `brief.*` | Заголовок, пояснение, продолжить, пример, очистить |
| `brief.city.*` | Локация, выбрать, неизвестное значение |
| `brief.date.*` | Дата, несуществующая дата, границы |

| `brief.category.*` | Категория, покрытие, ноль, ошибка |

| `brief.errors.*` | Заголовок сводки и ссылка к полю |

Не фиксировать магическое число ключей как условие приёмки. Проверять совпадение набора и форматных параметров между языками. Для динамических метрик предпочитать отдельную подпись «Профили в каталоге» и число, чтобы не собирать неверные окончания.

### 15.3 Редакторский контроль

Никаких «идеальный», «безупречный», «лучший», «магия выбора», «инновационная платформа» без проверяемого содержания. Заголовок называет действие или объект. Не употреблять «премиальный» как текст интерфейса. Качество выражается композицией и поведением.

Не строить предложения из цепочек двоеточий и тире. Служебные технические имена допустимы в документации, но не попадают в пользовательский путь.

## 16. Графика и зависимости от ассетов

Текущая приёмка фазы не зависит от получения 3D PNG. Типографическая карточка события, реальные данные и SVG обеспечивают законченную композицию.

| Группа | Состояние | Использование |
| --- | --- | --- |
| Geist | Есть локально | Основной шрифт с сохранённой лицензией |
| 16 SVG | Есть локально | Навигация и действия |
| Знак Tandau | Есть в макетах | Перенести в общий компонент; проверить favicon 16/32 px |
| Production desk | Ожидается | Дополнительная тематическая секция, не фон текста формы |
| Микрофон, камера, видеокамера, свет, площадка, флористика | Ожидаются | Редкие акценты категорий после приёмки |
| Календарь, бюджет, shortlist, comparison, brief, complete, folder, keycard, choice tray | Ожидаются | Будущие состояния и иллюстрации по назначению |

Файлы, размеры и требования заданы в [брифах](TANDAU_ASSET_BRIEFS.md) и [реестре](TANDAU_ASSET_INVENTORY.md). Не переименовывать их произвольно. При отсутствии файла не показывать битую картинку, пустую рамку «asset pending» или заменяющий 3D-эскиз.

После получения проверить прозрачность, чёрный без синего оттенка, масштаб, общую перспективу, отсутствие текста и соответствие назначению. Для декора использовать пустой alt, для смысловой картинки отдельное описание. Ширина и высота известны заранее, загрузка ниже первого экрана отложенная.

В одной секции не больше одного предметного акцента. Изображение не замещает label, цену, дату или сообщение об ошибке. Архивная графика в публичные шаблоны не подключается.

### 17.2 Что сохраняется

`matcher/data.py`, `Contractor`, `catalog.stats()`, `category_rows()`, `meta()`, `app/web.py` и механизм безопасной конфигурации уже существуют. Их не заменять упрощёнными копиями из старой документации.

Новый `app/brief.py` проверяет ввод веб-формы. Он не ранжирует профили и не вводит второй тип `SearchResponse`. В фазе 4 общие доменные проверки переносятся или переиспользуются через один источник правил. До этого совпадение канонических значений обеспечивается справочником каталога.

### 17.3 Перенос CSS

Нельзя одновременно подключить к `/` все стили дизайнбука и старый `app.css`. Сначала перенести токены и нужные компоненты в основной слой, затем удалить конфликтующие прежние определения только для заменённых компонентов.

Страницы дизайнбука продолжают подключать свои стили и сохраняют подпись образца. Старые auth-заглушки используют общий базовый шаблон и проверяются после смены токенов. Стили одного лендинга не должны менять глобально все `button` в чужом документе.

### 17.4 Данные в браузере

Сервер передаёт справочники и словарь строк для JS как безопасно сериализованный JSON. Не вставлять строки из CSV в исполняемый JavaScript вручную. Текст в DOM обновляется через `textContent` и значения полей.

Первый HTML содержит контент, категории и пример. Для первого отображения не нужен дополнительный сетевой запрос `/api/meta`. API остаётся для интеграции и будущих экранов.

### 17.5 Наблюдаемость без лишней системы

Ошибки загрузки каталога сохраняют существующее диагностическое поведение. Для формы достаточно серверной проверки и видимых ошибок. Аналитические SDK, трекеры, cookie-баннер ради несуществующей аналитики и внешние сервисы в фазе 1 не добавляются.

## 18. Последовательность выполнения

Пакеты выполняются по зависимостям. Указанные ниже результаты являются контрольными точками, а не обещанием уложить переработку в старые 40 минут.

### P1-A. Зафиксировать основу

Главный разработчик сверяет текущий код с разделом 2, запускает существующие проверки, фиксирует исходные скриншоты `/` и утверждённого макета. Создаёт список реально изменяемых файлов и не включает чужие незавершённые документы в коммит.

**Готово** — известна исходная версия, прежний сайт работает, перечень изменений ограничен фазой 1.

### P1-B. Общий визуальный слой

Перенести токены, шрифт, собственный знак, контейнеры, кнопки, навигацию и footer. Проверить основные шаблоны и обе auth-заглушки.

**Готово** — новое окружение отображается на 360, 768 и 1440 px; нет прежней палитры и случайных скруглений.

### P1-C. Лендинг с реальными данными

Собрать секции из раздела 6. Пример подключить по ID, числа каталога брать из существующих индексов. Все новые строки сразу провести через RU-ключи.

**Готово** — страница читается целиком, все CTA имеют назначение, примеры подписаны, нет выдуманных доказательств доверия.

**Готово** — валидный запрос доходит до `/app`; ошибка исправляется без потери остальных условий; Back, язык и refresh проверены.

### P1-E. Гостевой экран

Принять переводы от yassmn126, проверить длинные строки, клавиатуру, мобильные состояния и сценарии без JS. Исправить дефекты основного кода самостоятельно.

### P1-G. Документация и передача

Обновить README фактическими функциями, приложить проверенные ограничения и результаты тестов. Зафиксировать целевой набор файлов, выполнить push по рабочему процессу репозитория.

**Готово** — документация не объявляет готовыми авторизацию и движок; следующий разработчик понимает точки подключения.

### 18.1 Оценка объёма

Для текущей базы ориентир составляет 8–12 часов работы главного разработчика и 3–5 часов второго участника параллельно. Это оценка планирования, не измеренный срок. Наибольшая неопределённость связана с переносом общего CSS, сохранением черновика при навигации и проверкой переводов.

После P1-B пересмотреть оставшийся объём по фактическим проблемам. Если жёсткий дедлайн ближе, сначала закончить обязательный путь и использовать сокращения из раздела 23. Не выдавать урезанный объём за выполненные пункты полной приёмки.

Основной код, архитектура, серверная проверка, состояние черновика и дизайн компонентов остаются у главного разработчика. Ниже небольшие задачи, которые можно выполнять независимо.

**Файлы** — `app/i18n/kk.json`, `app/i18n/en.json`; замечания к RU отдельным списком, без переименования ключей.

**Приёмка** — одинаковые ключи и параметры форматирования; дата, цена и длинные названия читаются на 360 px. Перевод не утверждает, что поиск уже доступен.

**Приёмка** — инструкция не требует личного аккаунта или ключа модели. Пример не назван работающим движком. Никакие публикации и сообщения от имени команды эта задача не предусматривает.

Эти подпакеты уточняют существующие задачи. Не создавать дубликаты автоматически и не отдавать второму участнику всю продуктовую фазу.

## 20. Проверки реализации

Этот раздел описывает будущую проверку кода фазы 1. В текущем документальном изменении он не является отчётом о выполненной реализации.

### 20.1 Автоматические проверки

| Область | Значимые случаи |
| --- | --- |
| Нормализация бюджета | Пробелы трёх типов, ведущие нули, ноль, отрицательное, дробь, экспонента, предел передачи |

## 23. Риски и сокращение объёма

| Риск | Решение |
| --- | --- |
| Дизайнбук копируется целиком и ломает общие стили | Переносить согласованные токены и компоненты, проверять остальные маршруты |
| Оформление скрывает отсутствие поиска | Разделять личный черновик и подписанный пример |
| Поздние переводы | Главный разработчик фиксирует ключи заранее; фаза не закрывается одним RU-fallback |
| Новые 3D-файлы не пришли | Выпускать законченную типографическую композицию без placeholder-графики |
| Условия пропадают после входа | SessionStorage отдельно от auth cookie, короткий возврат на `/app` |
| Прямой URL смешивается со старым черновиком | Приоритет явного снимка и отсутствие частичного merge |
| Цена в подготовленном объяснении устарела | Сверять факты примера с каталогом |
| Фаза расширяется до CRM | Держать один запрос, одну категорию, пять условий |

Если требуется уменьшить объём, сначала убрать необязательный кастомный календарь, бюджетный ползунок и подключение 3D. Затем сократить декоративные переходы и второстепенную графику. Не сокращать обязательный формат, сохранение введённых условий, честность примера, ошибки, переводы и работоспособность CTA.

Если срок не позволяет выполнить весь обязательный объём, зафиксировать частично выполненную фазу и конкретный остаток. Не переименовывать недостающие функции в «готовый MVP».
